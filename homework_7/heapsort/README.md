# Задача 3. Heapsort

## Идея

Для сортировки по возрастанию нужна **maxheap**: каждый родитель не меньше своих детей, максимум стоит в `arr[0]`. Массив делится на две части: слева куча `arr[:end]`, справа уже отсортированный хвост `arr[end:]`

1. **Построение кучи.** Строим maxheap снизу вверх, как `makeheap` из задачи 1, только с обратным сравнением: опускаем узлы от `n // 2 - 1` к корню. Листья уже кучи, и когда опускаем узел, поддеревья его детей уже кучи
2. **Извлечение максимумов.** Пока в куче больше одного элемента, меняем `arr[0]` (максимум кучи) с последним элементом кучи `arr[end - 1]`. Максимум встает на свою позицию в начало хвоста, куча уменьшается на один элемент. Новая вершина может нарушать свойство кучи, поэтому опускаем ее (`sift_down`) внутри `arr[:end - 1]`

**Почему это верно.** Инвариант: `arr[:end]` это maxheap, хвост `arr[end:]` отсортирован, и каждый элемент кучи не больше любого элемента хвоста. На каждом шаге в хвост уходит максимум кучи, поэтому он не больше элементов хвоста и не меньше остальных элементов кучи. Когда куча уменьшается до одного элемента, этот элемент наименьший, и массив отсортирован

Сортировка идет на месте: используются только обмены внутри `arr`, функция возвращает `None`, как `list.sort`. `heapq`, `sorted()` и `list.sort()` не используются. Сравниваются элементы только через `<` и `>`, поэтому сортируются любые сравнимые значения, например строки

Heapsort **неустойчив**: обмен вершины с концом кучи может переставить равные элементы. Для чисел это не важно, но при сортировке записей по ключу равные записи могут поменять порядок

## Сложность

`n` это длина массива

* **Время O(n log n)** на любом входе. Построение кучи O(n), доказательство в [proof.md задачи 1](../makeheap/proof.md). Затем `n - 1` извлечений, каждое опускает вершину не глубже `floor(log2 n)` уровней, в сумме не больше `n log2 n` шагов. В вершину каждый раз попадает элемент с последнего уровня кучи, обычно один из наименьших, и он опускается почти до низа. Для различных элементов даже лучший случай Θ(n log n) (Schaffer, Sedgewick, 1993). Исключение массив из одинаковых элементов: опускание сразу останавливается, время O(n)
* **Память O(1)**: куча и отсортированный хвост лежат в самом массиве, `sift_down` итеративный, без рекурсии. Тест `test_in_place` проверяет через `tracemalloc`, что на 20 000 элементов пик выделенной памяти меньше 4 КБ, копия списка заняла бы около 160 КБ

Для сравнения: mergesort из homework_6 тоже O(n log n), но использует O(n) дополнительной памяти на срезы и слияния. `sorted()` это Timsort: O(n log n) в худшем случае, O(n) на уже упорядоченных участках, O(n) памяти

## Как это работает по шагам

Пример `[5, 2, 9, 1, 7, 3, 8]` (`make demo`):

```
строим maxheap, опускаем внутренние узлы с конца
  i = 2, элемент 9: [5, 2, 9, 1, 7, 3, 8]
  i = 1, элемент 2: [5, 7, 9, 1, 2, 3, 8]
  i = 0, элемент 5: [9, 7, 8, 1, 2, 3, 5]
maxheap: [9, 7, 8, 1, 2, 3, 5]

 шаг | максимум | куча               | отсортировано
   1 |        9 | [8, 7, 5, 1, 2, 3] | [9]
   2 |        8 | [7, 3, 5, 1, 2]    | [8, 9]
   3 |        7 | [5, 3, 2, 1]       | [7, 8, 9]
   4 |        5 | [3, 1, 2]          | [5, 7, 8, 9]
   5 |        3 | [2, 1]             | [3, 5, 7, 8, 9]
   6 |        2 | [1]                | [2, 3, 5, 7, 8, 9]

ответ: [1, 2, 3, 5, 7, 8, 9]
```

При построении девятка в узле `2` уже больше детей. Двойка опускается на место семерки. Пятерка из корня опускается на два уровня: на место девятки, затем на место восьмерки. Подробнее первый шаг извлечения: меняем `9` с последним элементом `5`, затем опускаем `5` в куче из шести элементов

```
      9                  5                  8
    /   \              /   \              /   \
   7     8     ->     7     8     ->     7     5
  / \   / \          / \   /            / \   /
 1   2 3   5        1   2 3            1   2 3

                 хвост [9]          хвост [9]
```

## Выводы

* **Рост времени.** При увеличении `n` в 10 раз время heapsort растет в 12.6 до 14.4 раза. Для `n log n` ожидаем `10 * log(10^4) / log(10^3) = 13.3` и `10 * log(10^5) / log(10^4) = 12.5`, это совпадает с измерениями. Время почти не зависит от порядка входа, как и следует из оценки Θ(n log n) для всех случаев
* **Heapsort и mergesort.** На случайных данных они примерно равны, heapsort медленнее на 0 до 20 процентов. Heapsort делает вдвое больше сравнений: на каждом уровне опускания два сравнения, на случайном массиве из 10^5 элементов около 3.0 млн против 1.5 млн у mergesort. Кроме того, его обращения к памяти прыгают по массиву от родителя к ребенку. Зато heapsort использует O(1) памяти против O(n). На упорядоченных массивах mergesort заметно быстрее: при слиянии одна половина быстро заканчивается, и остаток другой копируется одним `extend`. Heapsort от порядка не выигрывает, сначала он все равно строит кучу и перемешивает массив
* **sorted().** Встроенная сортировка быстрее в 16 раз на случайных данных и в сотни раз на упорядоченных. Timsort написан на C, а наши функции интерпретируются Python, каждое сравнение и обмен в цикле стоят дорого. Кроме того, Timsort находит уже упорядоченные участки и на возрастающем или убывающем массиве работает за O(n)
* **Повторы.** На массиве из 10 значений heapsort работает чуть быстрее, чем на случайном: при равенстве опускание останавливается раньше. `sorted()` ускоряется сильнее, примерно вдвое: при слиянии участков с длинными блоками равных значений Timsort переходит в режим galloping и копирует блоки целиком. Поэтому разрыв здесь больше, 19 до 29 раз

Время зависит от машины и запуска, это демонстрация, а не тест. Размеры можно задать: `make bench ARGS="1000 10000 100000 1000000"`
