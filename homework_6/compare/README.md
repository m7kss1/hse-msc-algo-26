# Задача 1. Compare

## Идея

**Mergesort** делит массив пополам, пока в частях не останется по одному элементу. Затем сливаем отсортированные половины: сравниваем их первые еще не выданные элементы и добавляем меньший в ответ. Когда одна половина закончилась, дописываем остаток другой. Так после каждого слияния получаем отсортированный массив

**Quicksort** берет последний элемент как опорный и раскладывает все элементы в три списка: меньше, равные и больше опорного. Списки меньших и больших сортируются рекурсивно, затем объединяются с равными. Каждый элемент меньшей части не превосходит опорный, а каждый из большей не меньше его, поэтому объединение отсортировано. Отдельная часть равных позволяет за один проход обработать массив одинаковых элементов

Обе функции возвращают новый массив и не меняют входной. Декоратор `timer` замеряет время через `perf_counter`, печатает его и возвращает результат функции. Измерение в `finally`, поэтому время выводится и при исключении, само исключение передается дальше. Замеряем только внешний вызов сортировки, иначе получили бы время каждой рекурсивной ветки

## Сложность

`n` это длина массива

* **Mergesort: время O(n log n)**: на каждом из O(log n) уровней деления слияния обрабатывают в сумме n элементов
* **Mergesort: память O(n)** на срезы и слияния, на каждом пути размеры сохраняемых частей убывают вдвое. Стек занимает O(log n)
* **Quicksort: время O(n log n)** в среднем при примерно сбалансированных разбиениях, **O(n^2)** в худшем случае: если каждый раз опорный наибольший или наименьший, размеры частей n, n-1 и так далее. Для одинаковых элементов время O(n)
* **Quicksort: память O(n^2)** в худшем случае: при неудачных разбиениях на стеке одновременно остаются списки длиной n, n-1 и так далее, поэтому их суммарный размер O(n^2). При сбалансированных разбиениях O(n)

У рекурсивного quicksort на неудачных разбиениях глубина достигает n, поэтому на достаточно длинном отсортированном массиве можно получить `RecursionError` из-за ограничения стека Python. Итеративный вариант из второй задачи этого ограничения не имеет

## Как это работает по шагам

Для `[4,1,3,2,3]` (`make demo`):

```
mergesort:
делим [4,1,3,2,3] на [4,1] и [3,2,3]
делим [4,1] на [4] и [1], сливаем в [1,4]
делим [3,2,3] на [3] и [2,3], сливаем в [2,3,3]
[1,4] + [2,3,3] = [1,2,3,3,4]

quicksort:
опорный 3: [1,2] | [3,3] | [4]
опорный 2: [1]   | [2]   | []
собираем [1,2] + [3,3] + [4] = [1,2,3,3,4]
```

## Сравнение времени

`make bench` запускает обе сортировки на одинаковых массивах длины 600: случайные разные числа с фиксированным seed, числа по возрастанию и одинаковые числа. Пример одного запуска, секунды:

```
массив             mergesort    quicksort
случайные           0.001672     0.000801
по возрастанию      0.001248     0.013201
одинаковые          0.001166     0.000038
```

На возрастающем массиве последний элемент каждый раз максимален, поэтому quicksort делает n почти полных проходов. У mergesort деление пополам не зависит от порядка. На одинаковых значениях quicksort завершает работу после одного разбиения, mergesort по-прежнему делит и сливает. Время зависит от машины и запуска, это демонстрация, а не тест с обязательным соотношением времен

Размер 600 выбран с учетом предела рекурсии Python. `make bench ARGS=800` позволяет задать другой размер, но на слишком большом отсортированном массиве quicksort может превысить предел стека
